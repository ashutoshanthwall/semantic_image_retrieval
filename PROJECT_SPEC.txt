PROJECT TYPE:
C++ + DSA + AI/ML + Computer Vision + Information Retrieval

PROJECT NAME:
C++-Based Semantic Image Retrieval System

ALTERNATIVE NAMES:
Intelligent Image Search Engine
Semantic Image Search Engine

REFERENCE REPOSITORY:
CompTech Winter School — image-finder
https://github.com/comptech-winter-school/image-finder

IMPORTANT:
The Winter School repository is architectural/reference inspiration,
NOT something we will blindly copy.

Its important architectural ideas include separating:
- embedding generation
- exact/simple retrieval
- HNSW retrieval
- search orchestration

Our implementation adapts those ideas into a strongly C++/DSA-oriented
architecture using Flickr30k.

====================================================================
1. PROJECT OBJECTIVE
====================================================================

Build a semantic image retrieval system in which a user can search
for images using natural-language meaning rather than filenames,
exact keywords, manually assigned tags, or folder names.

Example:
"a dog playing in snow"

Core concept:

TEXT QUERY
    ↓
CLIP TEXT ENCODER
    ↓
QUERY EMBEDDING
    ↓
VECTOR SEARCH
    ↓
MOST SEMANTICALLY SIMILAR IMAGE VECTORS
    ↓
IMAGE IDS
    ↓
METADATA LOOKUP
    ↓
IMAGE PATHS
    ↓
TOP-K RESULTS

Four major technical layers:
1. AI/ML representation → CLIP
2. Computer vision/image preprocessing → OpenCV
3. Data structures/retrieval algorithms → C++
4. Evaluation → Brute Force vs HNSW

Fundamental architecture:

Flickr30k
    ↓
Image preprocessing
    ↓
CLIP image embeddings
    ↓
Vector storage
    ↓
Retrieval indexes
    ├── Brute Force
    └── HNSW

Search:

User text query
    ↓
CLIP text embedding
    ↓
Query vector
    ↓
Search engine
    ↓
Brute Force OR HNSW
    ↓
Top-K image IDs
    ↓
Metadata lookup
    ↓
Image paths
    ↓
Results

5. IMAGE PREPROCESSING AND CLIP
====================================================================

OpenCV is responsible for:
- image loading
- image validation
- image manipulation
- preprocessing

OpenCV does NOT perform semantic understanding.

Conceptual pipeline:
Image
    ↓
OpenCV
    ↓
Load
    ↓
Validate
    ↓
Resize/crop as required
    ↓
Normalize as required
    ↓
CLIP-compatible input

CLIP provides:
IMAGE → embedding
TEXT → embedding

The embeddings occupy a shared semantic space.

The exact embedding dimensionality depends on the selected CLIP
model. Do NOT hard-code a dimension such as 512 throughout the
codebase. Treat dimension as configuration.

For every valid image:
image
  ↓
preprocessing
  ↓
CLIP image encoder
  ↓
floating-point vector
  ↓
save vector

Embedding generation is OFFLINE.

First execution:
Flickr30k
    ↓
CLIP
    ↓
~31k image embeddings
    ↓
Save to disk

Future execution:
Program starts
    ↓
Load saved embeddings
    ↓
Build/load retrieval index
    ↓
Ready

Do NOT regenerate every image embedding whenever search starts.

Recommended conceptual storage:
data/embeddings/
    image_embeddings.bin
    metadata.json
    manifest.json

Exact formats may change during implementation. The principle is:
embeddings must be persistent.

EmbeddingStore responsibilities:
- load embeddings
- save embeddings
- access embedding by ID
- validate dimensions
- provide iteration over vectors
- avoid unnecessary copying

Validate:
- expected dimension
- NaN values
- infinite values
- empty vectors
- invalid IDs

6. SIMILARITY
====================================================================

Use cosine similarity as the primary metric:

              q · x
cos(q,x) = -----------
           ||q|| ||x||

If vectors are normalized:
cos(q,x) = q · x

Maintain consistency between query and stored image embeddings.

Dedicated VectorMath module responsibilities:
dotProduct()
norm()
normalize()
cosineSimilarity()

7. COMMON RETRIEVAL INTERFACE
====================================================================

Define a common abstraction so SearchEngine can work with either
exact or approximate retrieval.

Conceptually:

class RetrievalIndex
{
public:
    virtual void insert(
        int id,
        const std::vector<float>& embedding
    ) = 0;

    virtual std::vector<int> search(
        const std::vector<float>& query,
        int k
    ) = 0;

    virtual ~RetrievalIndex() = default;
};

Architecture:

RetrievalIndex
       |
  +----+----+
  |         |
  ↓         ↓
Brute      HNSW
Force      Index

====================================================================
8. BRUTE-FORCE EXACT RETRIEVAL
====================================================================

For every query, compare the query against every image vector:

score = cosineSimilarity(query, image)

Brute force is:
- exact baseline
- ground truth
- validation reference

Use Top-K heap rather than fully sorting all scores when appropriate.

Conceptually:
for each image:
    score = similarity(query, image)
    add candidate to heap
    if heap size > K:
        remove worst candidate

Approximate complexity:
O(ND + N log K)
for N vectors and D-dimensional embeddings, ignoring smaller overheads.

DSA concepts:
- vectors/arrays
- linear search
- heaps
- priority queues
- sorting
- Top-K
- nearest-neighbor search
- complexity analysis

====================================================================
9. HNSW
====================================================================

HNSW = Hierarchical Navigable Small World.

It is an approximate nearest-neighbor structure based on multiple
graph layers.

Conceptually:
Higher layer:
    sparse graph → coarse navigation

Middle layers:
    intermediate connectivity

Layer 0:
    dense graph → detailed candidate search

Search:
Query vector
    ↓
Entry point
    ↓
Highest layer
    ↓
Greedy navigation
    ↓
Cannot improve further
    ↓
Move down
    ↓
Continue
    ↓
Layer 0
    ↓
Candidate exploration
    ↓
Top-K

Conceptual node:

struct HNSWNode
{
    int id;
    std::vector<float> embedding;
    std::vector<std::vector<int>> neighbors;
};

Conceptual HNSWIndex:
- entryPoint
- maxLevel
- M
- efConstruction
- efSearch
- nodes

Insertion conceptually:
New embedding
    ↓
Select random maximum level
    ↓
Start from entry point
    ↓
Search upper layers
    ↓
Find promising neighborhood
    ↓
Descend
    ↓
Search candidate neighbors
    ↓
Select neighbors
    ↓
Connect node
    ↓
Update reciprocal connections
    ↓
Prune excessive connections
    ↓
Continue

Search uses:
- graph traversal
- greedy movement
- distance/similarity computation
- candidate priority queues
- result priority queues

Parameters:
M = graph connectivity
efConstruction = construction/search effort during building
efSearch = search effort

These are empirical trade-offs.

Core research question:
"How much search latency can HNSW save while maintaining
sufficiently high retrieval recall compared with exact
brute-force search?"

DSA concepts:
- graphs
- adjacency lists
- weighted/similarity relationships
- graph traversal
- greedy algorithms
- priority queues
- heaps
- hierarchical structures
- nearest-neighbor search
- approximate nearest-neighbor search
- Top-K
- complexity analysis

12. BENCHMARKING AND EVALUATION
====================================================================

Compare:
Brute Force vs HNSW

For identical queries and embeddings.

Primary metrics:
1. Recall@5
2. Recall@10
3. Query latency
4. Speedup
5. Memory usage

Supporting measurements may include:
- index build time
- throughput
- average latency
- parameter sensitivity

For K=5:
Recall@5 =
    |Exact Top-5 ∩ HNSW Top-5|
    ---------------------------
              5

Brute force establishes the exact reference set.

Benchmark queries:
evaluation/queries.txt

Every algorithm receives exactly the same query set.

For each query:
1. Generate one query embedding.
2. Use the SAME query embedding for both indexes.
3. Run brute force.
4. Run HNSW.
5. Record latency.
6. Record Top-K IDs.
7. Calculate Recall@K.
8. Aggregate results.

Measure retrieval latency separately from neural embedding generation
latency when possible.

Speedup:
Brute-force latency
-------------------
HNSW latency

Evaluate multiple efSearch values, e.g.:
20, 40, 80, 120

Actual benchmark numbers must be measured. Illustrative values in
the architecture are NOT project results.

A useful analysis is the Recall@5 vs Latency trade-off.

====================================================================
22. CORE PRINCIPLES
====================================================================

1. Separate offline indexing from online querying.
2. CLIP provides semantic representation; it is NOT the retrieval engine.
3. OpenCV handles image preprocessing; it is NOT semantic search.
4. Brute Force provides exact retrieval and ground truth.
5. HNSW provides approximate nearest-neighbor retrieval.
6. The same RetrievalIndex abstraction supports both.
7. HNSW quality is measured against exact search.
8. Metadata is separate from vector storage.
9. Embeddings are generated offline and persisted.
10. The system is modular so components can be replaced independently.
11. C++ owns the core retrieval/DSA infrastructure.
12. Future features must not destabilize the core architecture.
